## 2.1 Формирование требований к системе

Требования выводятся из анализа предметной области (глава 1) и не дублируют введение.
Формулировки — от потребности, а не от реализации: не «система имеет», а «система должна обеспечивать».

### 2.1.1 Функциональные требования

Структурировать по группам акторов: пользователь, администратор, система (автоматические операции).
Каждое требование — атомарное и верифицируемое.

Примерные группы:
- Регистрация и идентификация пользователя через Telegram и web
- Получение, продление и отзыв конфигурации доступа
- Управление заявками и реестром разрешений (admin)
- Управление платёжным циклом и промокодами
- Автоматический мониторинг сроков и трафика, уведомления
- Техническая выдача клиентов на узлах 3x-ui через API
- Журналирование всех операций с фиксацией субъекта и основания
- Развёртывание серверных узлов через Ansible

### 2.1.2 Нефункциональные требования

- Воспроизводимость развёртывания: повторный запуск плейбука не должен нарушать состояние
- Конфигурируемость через переменные окружения без изменения кода
- Управление функциональными блоками через feature flags (FEATURES__*)
- Расширяемость топологии: добавление нового узла не требует изменения кода системы
- Устойчивость Telegram-бота: retry с backoff, graceful degradation при недоступности 3x-ui
- Изолированность компонентов: каждый компонент запускается и деплоится независимо

### 2.1.3 Проектные ограничения и допущения

Явно зафиксировать то, что намеренно не входит в рамки задачи:
- Многофакторная аутентификация и проверка состояния клиентского устройства — за рамками
- RBAC с гранулярными ролями — за рамками (два уровня: пользователь / администратор)
- Интеграция с конкретным платёжным шлюзом в боевом режиме — за рамками (предусмотрен demo gateway)
- Поддержка панелей, отличных от 3x-ui — за рамками текущей реализации
- Горизонтальное масштабирование backend — за рамками (одна инстанция)

Это снимает вопросы рецензента о том, «почему нет X».

## 2.2 Модель участников и сценариев использования

Раздел отвечает на вопрос «кто что делает» на уровне проектных сценариев.
Не пересекается с 2.4 (жизненный цикл): здесь — акторы и триггеры, там — состояния и переходы.

📊 **Диаграмма: Use Case (UML)** — одна диаграмма на весь раздел.
Акторы: Пользователь, Администратор, Система (автоматические процессы), 3x-ui API (внешняя система).
Включить только ключевые прецеденты, без перегрузки.

### 2.2.1 Участники системы

Четыре актора:
- **Пользователь** — взаимодействует через Telegram-бот и web-кабинет; инициирует запрос доступа, получает конфигурацию, продлевает подписку
- **Администратор** — взаимодействует через web-панель; управляет заявками, пользователями, узлами, планами; видит audit log
- **Система** — автономные процессы: мониторинг сроков и трафика, отправка уведомлений, синхронизация состояния с узлами
- **3x-ui API** — внешняя система, получающая команды технического изменения доступа; не инициирует взаимодействие самостоятельно

### 2.2.2 Пользовательские сценарии

Ключевые: регистрация через Telegram (/start), активация пробного периода, выбор плана и оплата, получение конфигурации, проверка статуса подписки, продление, обращение в поддержку, связывание аккаунтов (Telegram ↔ Web).

### 2.2.3 Административные сценарии

Ключевые: просмотр и обработка заявок на доступ, ручная выдача/отзыв доступа, блокировка пользователя, управление планами и промокодами, просмотр журнала операций, управление реестром разрешений.

### 2.2.4 Сценарии автоматической обработки

Отличие от пользовательских: триггер — не действие человека, а наступление события.
Ключевые: уведомление об истечении срока (за N дней), автоматический отзыв при истечении, синхронизация трафикового лимита с 3x-ui, обработка webhook платёжного шлюза, начисление реферального бонуса.

## 2.3 Проектирование общей архитектуры системы

Раздел отвечает на вопрос «из чего состоит система и как части взаимодействуют».
Обосновывает архитектурные решения — почему монорепозиторий, почему shared как единый доменный слой, почему бот и backend не общаются через HTTP.

📊 **Диаграмма: Компонентная диаграмма (UML Component)** — ключевая диаграмма всей главы.
Показать: пять компонентов (ansible, shared, backend, telegram_bot, frontend), внешние системы (3x-ui API, PostgreSQL, Redis, платёжный шлюз), связи и интерфейсы между ними.

### 2.3.1 Архитектурные уровни

Четыре уровня, выведенные из анализа главы 1:
1. **Инфраструктурный** — Ansible; развёртывание серверных узлов
2. **Data-plane** — Xray-core на узлах; передача трафика
3. **Node-level control-plane** — 3x-ui; конфигурирование узла
4. **Сервисный** — backend + telegram_bot + frontend; управление жизненным циклом

Разрабатываемая система проектируется как реализация уровней 1 и 4 с интеграцией в уровень 3 через API.

### 2.3.2 Состав подсистем

Пять компонентов монорепозитория и их роли:

| Компонент | Роль | Точка развёртывания |
|---|---|---|
| `ansible/` | Автоматизированное развёртывание серверных узлов | Рабочая машина оператора |
| `shared/` | Доменные модели и миграции БД | Монтируется в backend и telegram_bot |
| `backend/` | REST API — аутентификация, подписки, платежи, admin | Отдельный контейнер |
| `telegram_bot/` | Пользовательский интерфейс, техническая выдача доступа через 3x-ui | Отдельный контейнер |
| `frontend/` | Web-кабинет пользователя и панель администратора | Статика через Nginx |

Ключевое решение: `shared` — единственный источник истины доменных моделей; backend и telegram_bot работают с одной БД напрямую через SQLModel, без HTTP-взаимодействия между собой.

### 2.3.3 Взаимодействие подсистем

📊 **Диаграмма: Диаграмма последовательности (UML Sequence)** — для сценария «выдача доступа по заявке пользователя».
Показывает сквозное взаимодействие: пользователь → Telegram-бот → общий доменный слой/БД → администратор → frontend → backend → 3x-ui API → уведомление пользователю.
Это ключевой сценарий, раскрывающий ядро предметной области: формальное основание выдачи доступа, административное решение, техническое применение доступа и доставку конфигурации.

Покупка подписки и автоматическая выдача через реестр предварительно разрешённых субъектов рассматриваются как альтернативные основания выдачи доступа. Их можно описать текстом в 2.4 без отдельной sequence-диаграммы, чтобы не смещать акцент с управления жизненным циклом доступа на платёжный или справочный сценарий.

Остальные взаимодействия описать текстом: frontend ↔ backend (REST), backend ↔ PostgreSQL/Redis, telegram_bot ↔ 3x-ui API (HTTP через ClientManager).

### 2.3.4 Границы ответственности разрабатываемого сервиса

Явно обозначить, что сервис не делает:
- Не реализует новый VPN- или proxy-протокол
- Не заменяет панель 3x-ui — управляет ею через API
- Не хранит VPN-трафик и не является точкой маршрутизации
- Не предоставляет панель управления узлом для администратора — только сервисный уровень над ней

## 2.4 Проектирование жизненного цикла доступа

Центральный проектный раздел — предмет работы в операционном виде.
Описывает не реализацию, а спроектированную последовательность состояний и переходов.

📊 **Диаграмма: Диаграмма состояний (UML State Machine)** — жизненный цикл объекта AccessGrant/SubscriptionState.
Состояния: pending → approved/rejected → configured → active → expiring → expired/revoked.
Это вторая ключевая диаграмма главы.

### 2.4.1 Заявка на доступ

Два режима инициирования: пользователь подаёт явную заявку (AccessRequest, режим заявок включён) или доступ выдаётся автоматически после оплаты (без явной заявки).
Проектное решение: оба режима фиксируют основание выдачи — либо одобрение администратором, либо факт успешной оплаты. Основание хранится как поле модели, а не только в логе.

### 2.4.2 Принятие решения о выдаче доступа

Два пути: ручное одобрение администратором (admin workflow) и автоматическое по политике (после оплаты или для пользователей из AccessRegistryEntry).
Проектное решение: решение и его субъект фиксируются в AdminAuditLog независимо от пути — это обеспечивает единообразие аудита.

### 2.4.3 Техническая выдача и доставка конфигурации

Два потока технической выдачи доступа в зависимости от типа подписки:
- **Стандартный** (duration_days): создание клиента в 3x-ui с датой истечения → VpnClient + VpnClientDeployment
- **Трафиковый** (quota_bytes): создание клиента с лимитом байт → TrafficGrant + синхронизация с 3x-ui

Проектное решение: оба потока используют единый ClientManager как точку интеграции с 3x-ui API, но имеют независимые сервисы технической выдачи доступа для временной подписки и трафикового лимита.

Доставка конфигурации: subscription link передаётся пользователю через Telegram-бот; доступ к ссылке возможен и через web-кабинет (/subscription/:token).

### 2.4.4 Продление, отзыв и синхронизация состояния

Продление: обновление даты истечения / квоты трафика в доменном реестре и синхронизация с 3x-ui через ClientManager.
Отзыв: деактивация клиента на всех узлах, где развёрнут VpnClientDeployment, + запись причины и инициатора в AdminAuditLog.
Мониторинг: reminder_queue_service отслеживает приближение истечения и ставит задачи в очередь уведомлений; traffic_limited_sync_service периодически сверяет фактический расход с 3x-ui.

Проектное решение: синхронизация состояния всегда двусторонняя — доменный реестр является источником истины, состояние узла — целевым; расхождение между ними является аномалией, подлежащей разрешению.

## 2.5 Проектирование доменной модели

Раздел описывает структуру данных на уровне сущностей и связей.
Не описывает DDL или конкретные типы колонок — это глава 3.

📊 **Диаграмма: ER-диаграмма (или UML Class с атрибутами)** — ключевые сущности и связи.
Не нужно включать все 30+ полей — только ключевые атрибуты и связи между группами.
Рекомендуется разбить на два уровня детализации: обзорная схема групп + детализация одной-двух ключевых групп (например, access + vpn).

### 2.5.1 Пользователь и каналы идентификации

Центральная сущность — AppUser; два канала: TelegramAccount (Telegram ID, username) и WebAccount (email, hashed password).
Проектное решение: каналы независимы и могут существовать по отдельности; связывание происходит через IdentityLinkToken с ограниченным сроком действия. Это позволяет пользователю начать с Telegram и привязать web позже — или наоборот.

WebSession хранит JWT-сессии web-канала; WebAuthChallenge — одноразовые токены email-аутентификации (без хранения пароля в открытом виде).

### 2.5.2 Заявка, разрешение и выданный доступ

AccessRequest — модель заявки с полями субъекта, статуса и основания решения.
AccessGrant — факт выданного доступа с привязкой к пользователю и типу гранта.
AccessRegistryEntry — предварительно одобренный список; пользователи из него получают доступ без явной заявки.

Проектное решение: все три модели существуют независимо — гранты могут существовать без заявки (автоматическая выдача после оплаты), заявки могут быть отклонены без создания гранта.

### 2.5.3 Подписка, срок действия и трафиковые ограничения

SubscriptionState — текущий статус подписки пользователя (expires_at, trial_activated_at, blocked_at).
SubscriptionGrant — отдельная запись каждого периода подписки с основанием.
TrafficState — текущий расход трафика; TrafficGrant — выданная квота.

Проектное решение: два параллельных потока (временной и трафиковый) проектируются как независимые — пользователь может иметь подписку только одного типа одновременно, но система хранит историю по обоим.

### 2.5.4 Топология узлов доступа

VpnLocation — географическая точка (название, код).
VpnControlPlane — конкретная панель 3x-ui на узле (api_base_url, subscription_base_url, provider).
VpnAccessPoint — входящее соединение (inbound) на панели; точка, к которой привязываются клиенты.
VpnClient — учётная запись пользователя на панели; VpnClientDeployment — привязка клиента к конкретному VpnAccessPoint.

Проектное решение: топология сидируется из переменных окружения при старте сервиса (VpnTopologyService), а не хранится статично в коде. Это позволяет добавить новый узел изменением конфигурации без пересборки образа.

### 2.5.5 Аудит и история операций

AdminAuditLog — запись каждого административного действия: субъект (кто), действие (что), объект (над чем), время, основание.

Проектное решение: запись в журнал производится на уровне сервисного слоя, а не триггерами БД — это обеспечивает возможность фиксировать бизнес-контекст (основание), а не только факт изменения данных.

Plan, PaymentOrder, PaymentAttempt, PaymentWebhookEvent — цепочка платёжного цикла. PromoCode / PromoRedemption, ReferralEdge / ReferralReward — механики роста. Описываются кратко — они являются вспомогательными относительно основного предмета работы.

## 2.6 Проектирование интерфейсов взаимодействия

Раздел отвечает на вопрос «через какой канал какие операции доступны и почему».
Не описывает UI-детали (цвета, кнопки, экраны) — это не предмет проектирования ВКР.

### 2.6.1 Telegram-бот как основной пользовательский интерфейс

Архитектура бота — три слоя внутри компонента:
- **Presentation** — роутеры и хэндлеры (start, subscriptions, payments, referrals, admin, help, support, users); обрабатывают входящие события и формируют ответы
- **Services** — бизнес-логика выдачи доступа, жизненного цикла, подписок, платежей и др.; не зависят от Telegram-специфики
- **Infrastructure** — ClientManager + ApiConnection; инкапсулируют HTTP-взаимодействие с 3x-ui API

Проектное решение: сервисный слой не импортирует ничего из Telegram-специфичных модулей — это позволяет тестировать бизнес-логику изолированно.

Middleware-цепочка: ContextMiddleware (извлекает chat_id, user_id в thread-local контекст) → MaintenanceModeMiddleware (bypass для администратора).

Область ответственности бота: все пользовательские операции самообслуживания + техническую выдачу доступа через 3x-ui. Администрирование через бота — только команды быстрого доступа; основная admin-функциональность — в web-панели.

### 2.6.2 Web-кабинет пользователя

SPA на Vue 3 с защищёнными маршрутами (requiresAuth). Зона `/app/*`:
- Overview — текущий статус подписки
- Subscriptions — управление подпиской
- Purchase — выбор плана и оплата
- Payments — история платежей
- Profile — профиль и связывание аккаунтов
- Help — инструкции по подключению

Проектное решение: web-кабинет является параллельным, а не резервным каналом — набор операций совпадает с Telegram-ботом, но web предпочтителен для задач, требующих просмотра истории и навигации между разделами.

### 2.6.3 Web-панель администратора

Маршрут `/{VITE_ADMIN_PATH}` — путь задаётся переменной окружения и отсутствует в исходном коде явно. Это проектное решение безопасности: панель не обнаруживается сканером по предсказуемому пути.

Функциональность AdminPanel: управление заявками, пользователями, подписками, платежами, просмотр журнала операций.

Проектное решение: административные операции сосредоточены в web-интерфейсе, а не в Telegram-боте — это обосновано структурными ограничениями чатового канала (см. 2.6.4).

### 2.6.4 Разграничение интерфейсов по типам операций

| Тип операции | Telegram-бот | Web-кабинет | Admin web-панель |
|---|---|---|---|
| Регистрация и вход | ✓ (по Telegram ID) | ✓ (email) | — |
| Получение конфигурации | ✓ (основной) | ✓ (дублирующий) | — |
| Проверка статуса | ✓ | ✓ | — |
| Продление подписки | ✓ | ✓ | — |
| Оплата | ✓ | ✓ | — |
| Просмотр истории платежей | — | ✓ | ✓ |
| Управление заявками | — | — | ✓ |
| Ручная выдача/отзыв доступа | — | — | ✓ |
| Просмотр журнала операций | — | — | ✓ |
| Управление пользователями | Команды быстрого доступа | — | ✓ (полный) |

Обоснование: Telegram эффективен для событийных и коротких action-сценариев; web — для задач с историей, фильтрацией и навигацией; административные операции требуют контекста и не подходят для чатового канала.

## 2.7 Проектирование инфраструктурного уровня

Раздел описывает проектные решения по автоматизации развёртывания и сопровождения серверных узлов.
Детали конкретных команд и конфигурационных параметров — в главе 3.

### 2.7.1 Роль инфраструктурного слоя в системе

Инфраструктурный уровень закрывает начальный этап, который во всех рассмотренных аналогах остаётся ручным: подготовку серверного узла к работе.
Проектное решение: Ansible-плейбуки являются частью системы, а не вспомогательным инструментом — они версионируются в монорепозитории и обеспечивают воспроизводимость развёртывания как требование, а не как опцию.

### 2.7.2 Инфраструктурные роли и опорные плейбуки

Основной акцент — не на полном перечне плейбуков, а на ролях Ansible и разделении инфраструктурных обязанностей.

| Роль | Назначение |
|---|---|
| `server_baseline` | Первичная подготовка сервера: SSH-hardening, UFW, базовые пакеты, системные настройки |
| `certbot_setup` | Выпуск и сопровождение TLS-сертификатов |
| `xui_app` | Установка и конфигурирование 3x-ui |
| `nginx_proxy` | Настройка reverse-proxy и публичного web-контура узла |
| `bot_server` | Подготовка хоста приложения, Nginx и опциональной инфраструктуры деплоя |
| `migration_manager` | Вспомогательный перенос или подготовка данных панели |

В тексте главы достаточно выделять два опорных плейбука:

| Плейбук | Назначение | Роли |
|---|---|---|
| `panel_only.yml` | Подготовка узла доступа: сертификаты, 3x-ui и reverse-proxy без миграции данных | `certbot_setup`, `xui_app`, `nginx_proxy` |
| `bot_server.yml` | Подготовка хоста приложения: сертификаты, Nginx и опциональная инфраструктура деплоя | `certbot_setup`, `bot_server` |

Остальные плейбуки (`initial_setup.yml`, `site.yml`, `panel_xver_mask.yml`, `migration_only.yml`, `validate_stack.yml` и др.) можно упоминать как служебные или операционные варианты, но не делать их самостоятельной основой архитектурного описания. Для `panel_only.yml` важно помнить: режим `xver` применяется через значение по умолчанию роли `nginx_proxy`, если переменная не переопределена.

### 2.7.3 Развёртывание сервисных компонентов

Сервисные компоненты (backend, telegram_bot, frontend, PostgreSQL, Redis) развёртываются через Docker Compose.
Два файла: `docker-compose.yml` (разработка, локальная сборка) и `docker-compose.prod.yml` (продакшн, образы из реестра).

Плейбук `bot_server.yml` автоматизирует подготовку хоста приложения; сами сервисные контейнеры разворачиваются через Docker Compose.

Проектное решение: сервисы не делят сетевое пространство с VPN-узлами — backend и bot могут работать на отдельном хосте, взаимодействуя с 3x-ui API по HTTP. Это изолирует сервисный уровень от инфраструктурного.

Конфигурация передаётся через `.env.local` и переменные окружения — никаких конфигурационных файлов в коде. Feature flags (`FEATURES__*`) управляют набором активных функциональных блоков без пересборки.

### 2.7.4 Процедуры обслуживания и обновления инфраструктуры

Проектируются как отдельные идемпотентные операции:

| Плейбук | Назначение |
|---|---|
| `update_panel.yml` | Обновление 3x-ui до новой версии |
| `update_system.yml` | Обновление системных пакетов |
| `certificates_only.yml` | Принудительный выпуск сертификата |
| `renew_certs_now.yml` | Принудительное обновление истекающего сертификата |
| `migration_only.yml` | Применение миграций данных без деплоя |
| `validate_stack.yml` | Проверка корректности состояния стека |

Проектное решение: операции обслуживания изолированы от полного деплоя — оператор может обновить только сертификат или только панель, не затрагивая остальное.

## 2.8 Обоснование выбора технологий

Выбор обосновывается применительно к задаче — не как перечень популярных инструментов, а как аргументированное соответствие требованиям.

### 2.8.1 Backend и общий доменный слой

**FastAPI** — асинхронный Python-фреймворк; OpenAPI-спецификация генерируется автоматически, что упрощает интеграцию с frontend. Альтернативы (Django REST Framework, Flask) проигрывают по нативной поддержке async и автоматической документации.

**SQLModel** — объединяет SQLAlchemy ORM и Pydantic-валидацию в одной модели; позволяет использовать один класс как схему БД и как схему валидации API. Это исключает дублирование моделей между shared и backend.

**Alembic** — управление миграциями схемы БД; запускается как отдельный контейнер (`alembic` service) до старта основных сервисов, что гарантирует актуальность схемы при деплое.

### 2.8.2 Пользовательские интерфейсы

**pyTeleBot (async)** — официальная Python-библиотека Telegram Bot API с поддержкой middleware-цепочки и async-обработчиков. Middleware-архитектура позволяет реализовать ContextMiddleware и MaintenanceModeMiddleware без изменения хэндлеров.

**Vue 3 + TypeScript** — реактивный SPA-фреймворк; Composition API упрощает разделение логики по доменам (auth, subscriptions, payments). TypeScript обеспечивает типизацию API-контрактов между frontend и backend.

**Vue Router** — встроенный роутер с navigation guards; `ensureSession()` в beforeEach реализует защиту маршрутов без дополнительных библиотек.

### 2.8.3 Хранилища данных и фоновые процессы

**PostgreSQL 15** — реляционная СУБД; выбор обусловлен строгой схемой доменных моделей (внешние ключи, транзакции, audit log). Документоориентированные БД не подходят для модели с явными связями между AccessRequest, AccessGrant, VpnClient и AdminAuditLog.

**Redis 7** — используется как кэш (снижение нагрузки на PostgreSQL при частых запросах конфигурации) и как очередь задач (reminder_queue_service). Fallback на in-memory при недоступности Redis предусмотрен в конфигурации.

### 2.8.4 Инфраструктурные средства

**Ansible** — декларативный IaC-инструмент; идемпотентность ролей гарантирует одинаковый результат при повторном запуске. Альтернатива (Terraform) ориентирована на выделение облачных ресурсов, а не на конфигурирование серверного ПО — для задачи развёртывания 3x-ui, Nginx и Certbot Ansible предпочтительнее.

**Docker Compose** — оркестрация сервисных контейнеров; `depends_on` с `condition: service_healthy` обеспечивает порядок старта (PostgreSQL → Redis → Alembic → backend/bot). Kubernetes не рассматривается как избыточный для однонодового сервисного развёртывания.
