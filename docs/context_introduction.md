# Контекст для написания введения ВКР

**Тема:** Разработка автоматизированного сервиса защищённого удалённого доступа с управлением на базе интерфейса чат-бота

---

## 1. Краткая характеристика разрабатываемой системы

Система — это программный комплекс, автоматизирующий полный жизненный цикл защищённого удалённого доступа: от развёртывания серверной инфраструктуры до выдачи, сопровождения и отзыва доступа конечного пользователя.

**Подтверждённые модули (реализованы в коде):**

| Модуль | Технология | Назначение |
|---|---|---|
| `backend/` | FastAPI 0.135, Python | REST API: авторизация, подписки, платежи, admin-маршруты |
| `telegram_bot/` | pytelegrambotapi 4.27, asyncio | Основной пользовательский интерфейс через Telegram |
| `shared/` | SQLModel, SQLAlchemy 2.0, Alembic | Общие модели БД, репозитории, миграции |
| `frontend/` | Vue 3.5, TypeScript, Vite | Web-кабинет пользователя и административная панель |
| `ansible/` | Ansible | Автоматизированное развёртывание инфраструктуры |
| `tests/` | pytest, pytest-asyncio | Unit, smoke и integration-тесты |

**Хранилища:** PostgreSQL 15 (постоянные данные), Redis 7 (кэш, очереди планировщика).

**Запуск:** Docker Compose (dev и prod конфигурации), сетевая топология через Ansible-роли: `server_baseline`, `xui_app`, `nginx_proxy`, `certbot_setup`, `bot_server`, `migration_manager`.

**Подтверждённые функции системы:**
- Регистрация пользователей через web (email + код подтверждения + JWT-сессии) и через Telegram-бота
- Связывание Telegram-аккаунта с web-аккаунтом
- Выдача доступа: временно-ограниченного (`standard`) и трафик-ограниченного (`traffic_limited`)
- Управление жизненным циклом: подача заявки → (авто- или ручное одобрение) → создание клиента в X-UI панели → уведомление пользователя → мониторинг срока/трафика → напоминания → продление/отзыв
- Платёжный контур: создание заказов, webhook-приём, fulfillment, демо-шлюз для тестирования
- Промокоды, реферальная программа с конфигурируемыми правилами начисления бонусных дней
- Административная панель: управление пользователями, заявками, доступами, журнал действий
- Конфигурирование через env-переменные и feature flags (ACCESS_REQUESTS_ENABLED, REFERRALS, MAIL__ENABLED и др.)
- CI через GitHub Actions

**Что НЕ реализовано (подтверждено отсутствием в коде):** 2FA/MFA, RBAC для нескольких администраторов, rate limiting, мониторинг состояния VPN-соединения на стороне клиента.

## 2. Контекст предметной области

### Объект и предмет исследования

- **Объект:** процессы организации защищённого удалённого доступа к сетевым ресурсам и управления жизненным циклом доступа.
- **Предмет:** методы и программные средства автоматизации развёртывания, выдачи и управления доступом с использованием чат-бот-интерфейса и web-панели.

### Сценарии применения системы (подтверждены кодом и конфигурацией)

1. **Корпоративный / команда** — администратор управляет заявками и пользователями через web-панель; сотрудники получают доступ через Telegram-бота или web-кабинет.
2. **B2C** — пользователь самостоятельно оплачивает план доступа, получает конфигурацию без участия администратора.
3. **Open-source / личное использование** — развёртывание по документации через Ansible и Docker Compose; адаптация через env-конфигурацию.

### Технологический контекст

Система интегрируется с **X-UI (3x-ui)** как control-plane узла доступа (подтверждено именованием роли `xui_app` и кодом `ClientManager`). 3x-ui поддерживает протоколы Vmess, Vless, Trojan, Shadowsocks, WireGuard; управление — через web-UI без документированного REST API для внешних систем [официальный репозиторий 3x-ui, https://github.com/MHSanaei/3x-ui].

## 3. Проблема, на решение которой направлена работа

**Ручной процесс выдачи и сопровождения удалённого доступа** порождает структурные ограничения:

1. Администратор выполняет каждый шаг вручную: подготовка сервера → установка панели → создание пользователя → передача конфигурации → контроль срока → продление или отзыв доступа.
2. Отсутствует единый реестр выданных доступов с историей действий.
3. Пользователь зависит от доступности администратора при каждом запросе.
4. При ручной работе с конфигурациями и ключами высок риск ошибок и утечки данных.
5. Существующие панели управления (3x-ui, OpenVPN Access Server) решают задачу технической настройки клиентов, но не предоставляют пользовательского канала самообслуживания с встроенным управлением жизненным циклом подписки.

Разрыв между уровнем control-plane (серверная панель) и уровнем пользователя требует либо ручного администрирования, либо разработки интегрирующего слоя — что и составляет предмет настоящей работы.

Согласно ACM Computing Surveys (Bringhenti et al., 2023): «ручная оркестрация сетевых политик безопасности более не является осуществимой в современных сетевых окружениях» [doi:10.1145/3616401].

## 4. Актуальность темы

### Рост удалённой работы — подтверждённые данные

- По данным Eurostat, доля занятых, работающих из дома в ЕС (возраст 20–64 года), выросла с 5,5% в 2019 году до 12,3% в 2020-м и 13,5% в 2021-м — прирост более чем вдвое за два года [Eurostat, DDN-20221108-1, 2022].
- Европейская комиссия (JRC, документ JRC120945, 2021) фиксирует структурный характер перехода к дистанционной работе и указывает на необходимость соответствующей инфраструктуры [doi: JRC120945].
- МОТ (ILO, 2021) публикует доклад «Working from Home: From Invisibility to Decent Work», охватывающий масштаб явления и нормативный аспект обеспечения безопасности удалённого труда.
- По оценке BLS (U.S. Bureau of Labor Statistics, 2024), структурное увеличение доли дистанционной занятости устойчиво сохраняется после пандемии.

### Рост спроса на средства защищённого доступа

- Gartner (октябрь 2022) прогнозировал, что к 2025 году не менее 70% новых развёртываний удалённого доступа будут реализованы по модели ZTNA, а не традиционного VPN (в 2021 году — менее 10%); расходы на сетевую безопасность растут на 11,3% в год [Gartner Press Release, 2022-10-13].
- NIST SP 800-46 Rev. 2 (2016) устанавливает требования к корпоративной инфраструктуре удалённого доступа, включая политику аутентификации, управление доступом и управление уязвимостями.

### Разрыв между теорией и практикой для малого и среднего применения

Крупные решения (OpenVPN Access Server с REST API, корпоративные ZTNA-платформы) требуют лицензионных расходов и квалифицированного администрирования. Лёгкие панели (3x-ui) не предоставляют пользовательского интерфейса самообслуживания. Нет готового open-source решения, объединяющего: автоматизированное развёртывание + управление жизненным циклом + доступный пользовательский интерфейс.

### Интерфейс чат-бота как канал управления

Telegram Bot API (официальная документация, текущая версия 9.x) предоставляет механизм webhook / long polling, slash-команды, inline-клавиатуры и callback-запросы — достаточные для реализации полного сценария самообслуживания без установки отдельного приложения пользователем. Академический обзор Caldarini et al. (MDPI Information, 2022, doi:10.3390/info13010041) фиксирует расширение применения чат-ботов в задачах автоматизации сервисных процессов.

### Существующие системы управления доступом

| Система | Тип | Ограничения |
|---|---|---|
| **OpenVPN Access Server** | Коммерческий продукт, REST API (Swagger) | Платный, нет встроенного канала пользователя, требует отдельной разработки интеграции |
| **WireGuard** | Протокол (NDSS 2017, Donenfeld) | Нет встроенной панели управления пользователями |
| **3x-ui** | Open-source web-панель | Нет документированного API для внешних систем, нет канала пользовательского самообслуживания |
| **Outline (Jigsaw/Google)** | Open-source, REST Management API | Не предполагает платёжного контура, ограничен по сценариям управления |

**Вывод:** ни одно из рассмотренных решений не закрывает полный цикл: автоматизированное развёртывание + управление жизненным циклом подписки + доступный пользовательский канал + административная панель + возможность самостоятельного развёртывания как open-source. Это формирует нишу, в которой работа занимает оригинальную позицию.

### Нормативные и технические стандарты

- RFC 4301 (IETF, 2005) — базовая архитектура безопасности IP, определяет IPsec и туннельный режим.
- RFC 8446 (IETF, 2018) — TLS 1.3 как транспорт для management API.
- NIST SP 800-207 (2020) — архитектура нулевого доверия; актуальна для концептуального позиционирования системы.
- NIST SP 800-46 Rev. 2 (2016) — руководство по безопасности корпоративного удалённого доступа; задаёт требования, которым отвечает проектируемая система.

## 6. Предварительная формулировка цели работы

Разработать автоматизированный сервис защищённого удалённого доступа, обеспечивающий развёртывание серверной инфраструктуры, управление пользователями и полный жизненный цикл выдачи доступа посредством интерфейса Telegram-бота и web-панели.

---

## 7. Предварительный перечень задач работы

1. Проанализировать предметную область защищённого удалённого доступа и существующие подходы к управлению VPN/прокси-сервисами.
2. Сформировать функциональные и нефункциональные требования к разрабатываемой системе.
3. Спроектировать модульную архитектуру сервиса, включая инфраструктурный, серверный, пользовательский и административный уровни.
4. Разработать модуль автоматизированного развёртывания серверной инфраструктуры на базе Ansible.
5. Реализовать backend API и общий доменный слой (`shared`) для управления пользователями, заявками, подписками и точками доступа.
6. Реализовать Telegram-бота как основной пользовательский интерфейс выдачи и сопровождения доступа.
7. Реализовать web-кабинет пользователя и административную панель.
8. Провести проверку работоспособности системы на типовых сценариях использования.

## 8. Практическая значимость

**Подтверждённые применения (соответствуют реализованным функциям системы):**

- Внутренний сервис удалённого доступа для команды или организации: администратор управляет заявками и пользователями через web-панель, сотрудники получают доступ через Telegram-бота.
- B2C-сервис: пользователь самостоятельно выбирает план, оплачивает и получает конфигурацию без участия администратора.
- Open-source решение: система может быть развёрнута самостоятельно по документации и адаптирована под конкретную инфраструктуру; отсутствие привязки к закрытой платформе.
- Учебный стенд по DevOps, backend-разработке и автоматизации инфраструктуры.

**Ключевое свойство, определяющее практическую значимость:** система объединяет в единый сервис задачи, которые в существующих решениях решаются раздельно и требуют ручной интеграции — автоматизированное развёртывание, управление жизненным циклом доступа и интерфейс пользовательского самообслуживания.

## 9. Какие сведения ещё необходимо уточнить для написания полноценного введения

### Обязательно уточнить перед написанием

1. **Научный руководитель и кафедра** — необходимы для корректного оформления формулировки «в соответствии с заданием кафедры» или аналогичных административных фраз.
2. **Официальная формулировка направления подготовки** — код и полное наименование направления, профиль, год поступления (нужно для точного указания «магистрант направления 09.04.03 "Прикладная информатика"» или иного).
3. **Год защиты** — влияет на временно́й контекст актуальности.
4. **Были ли проведены апробация или тестирование системы на реальных пользователях?** — если да, это существенно усиливает раздел практической значимости.
5. **Есть ли акт внедрения или сотрудничество с организацией?** — если есть, упоминается во введении.
6. **Название организации или учебного заведения, в интересах которого выполняется ВКР** (если применимо).

### Желательно уточнить

7. **Методы исследования** — что именно использовалось: системный анализ, объектно-ориентированное проектирование, экспериментальное тестирование? Перечень методов — стандартный элемент введения ВКР.
8. **Формулировка «объект исследования»** — согласовать с научным руководителем: «процессы организации защищённого удалённого доступа» или иная.

### Что для введения не нужно

- Детали реализации платёжного контура, реферальной программы, промокодов — они не влияют на актуальность, цель и задачи на уровне введения.
- Конкретные параметры конфигурации (имена env-переменных, версии зависимостей).
- Детали структуры базы данных и миграций.
- Описание CI/CD-конфигурации.

Все эти элементы относятся к основной части ВКР (главы 2–3) и в введении не раскрываются.
