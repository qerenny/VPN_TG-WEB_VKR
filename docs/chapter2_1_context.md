## 1. Логика вывода требований

### Откуда берутся требования

Требования раздела 2.1 должны прямо вытекать из анализа главы 1 — иначе они превращаются в произвольный список функций, не связанный с обоснованием темы. Каждое требование должно отвечать на вопрос: «какую конкретную проблему предметной области оно устраняет?»

Цепочка вывода: **структурная проблема → проектная потребность → требование**.

| Проблема (глава 1) | Проектная потребность | Требование |
|---|---|---|
| Ручная выдача доступа — без фиксации основания, риск рассогласования записей | Явный, прослеживаемый акт выдачи | Система должна фиксировать основание каждого выданного доступа |
| Отсутствие самообслуживания: любой шаг требует обращения к администратору | Пользовательский интерфейс самообслуживания | Система должна обеспечивать пользователю самостоятельный запрос, получение и продление доступа |
| Ручной мониторинг сроков и трафика не масштабируется | Автоматические процессы контроля | Система должна автоматически отслеживать истечение срока и трафикового лимита |
| Ручной отзыв при множестве узлов — точка рассогласования | Атомарный отзыв со всех узлов | Система должна деактивировать клиента на всех узлах при отзыве доступа |
| Развёртывание узла — ручной процесс, неповторимый без документации | Декларативное воспроизводимое развёртывание | Система должна поддерживать автоматизированное развёртывание серверных узлов |
| Отсутствие единого реестра: состояние разрознено между панелью, таблицей, перепиской | Единый источник истины доменного состояния | Система должна хранить централизованный реестр доступов с историей операций |
| Аналоги не интегрируют жизненный цикл и технический уровень | Интегрирующий сервисный слой над control-plane | Система должна управлять клиентами на узлах через API панели управления |

### Что из анализа аналогов влияет на требования

- Ни один из прямых аналогов (AltShop, Bedolaga, VPNMarket, Remnashop) не обеспечивает IaC-развёртывание узлов как часть системы → это формирует требование к инфраструктурному уровню.
- Большинство аналогов не имеют явного реестра заявок с прослеживаемым основанием решения → требование к явной модели заявки и аудит-журналу.
- Пользовательский канал у аналогов — Telegram или web, но не оба с возможностью связывания → требование к dual-channel идентификации и IdentityLink.
- Ни один аналог не разграничивает чётко ручной и автоматический режим выдачи доступа → требование к управляемому переключению режима.

### Зачем делить требования на три группы

**Функциональные** отвечают на «что система делает для акторов» — они верифицируемы и связаны с поведением.

**Нефункциональные** отвечают на «как система это делает» — они накладывают ограничения на качество, надёжность, сопровождаемость. Их нельзя проверить одним тест-кейсом. Если записать их в функциональный список, структура ломается.

**Ограничения и допущения** — явная фиксация того, что намеренно исключено. Без этого рецензент начнёт задавать вопросы «почему нет MFA», «почему нет Kubernetes» — и ответа в тексте не найдёт. Это не признание слабости, а часть инженерной добросовестности.

### Зачем группировать по акторам

Альтернатива — группировка по подсистемам (регистрация, подписки, платежи...) — ведёт к смешению уровней и затрудняет проверку полноты. Группировка по акторам естественно отделяет:
- что пользователь инициирует сам,
- что администратор контролирует,
- что система делает без вмешательства человека.

Это также предотвращает дублирование: «уведомление» — это не пользовательское требование (пользователь его не запрашивает), это автоматический процесс.

### Где граница между требованием и архитектурным решением

**Требование:** «Система должна обеспечивать продление доступа без участия администратора».
**Архитектурное решение:** «Продление реализуется через сервис subscription_provisioning_service, который обновляет запись VpnClient через ClientManager».

Требование не называет компоненты, методы, классы, таблицы БД. Оно описывает поведение с точки зрения актора или системы в целом. Если формулировка требует знания архитектуры, чтобы её понять — это уже не требование, а проектное решение.

**Тест:** можно ли проверить выполнение требования, не зная ничего о внутреннем устройстве системы? Если да — это требование. Если нет — это решение.

## 2. Контекст для 2.1.1 «Функциональные требования»

### Логика группировки

#### Группа 1: Пользователь

**Зачем:** устранить зависимость пользователя от администратора в операциях самообслуживания — ключевая проблема предметной области (раздел 1.2 главы 1).

**Процессы:** идентификация, запрос доступа, получение конфигурации, продление, оплата, просмотр статуса.

**Риск смешения с реализацией:** не говорить «через команду /start», «через хэндлер», «через REST-метод» — только что пользователь может делать.

#### Группа 2: Администратор

**Зачем:** предоставить инструмент контроля и управления жизненным циклом доступа, заменив ручные разрозненные операции единым контуром.

**Процессы:** обработка заявок, ручная выдача/отзыв, управление пользователями, просмотр журнала, управление планами.

**Риск:** не приписывать администратору то, что в системе делается автоматически (уведомления, синхронизация — это группа 3).

#### Группа 3: Система (автоматический контур)

**Зачем:** снять с администратора мониторинговую нагрузку, которая при ручном процессе возрастает линейно с числом пользователей (глава 1.2).

**Процессы:** мониторинг сроков, мониторинг трафика, отправка уведомлений, автоматический отзыв, синхронизация с узлами, обработка платёжных событий.

**Риск:** не смешивать с функциями администратора — автоматический контур не принимает решения, он исполняет политики.

#### Группа 4: Интеграционный уровень (внешние системы)

**Зачем:** явно указать, что система взаимодействует с 3x-ui API и (потенциально) с платёжным шлюзом как с внешними системами — это формирует требования к интеграции, не путая их с функциями акторов.

**Осторожно:** здесь легко соскользнуть в детали реализации. Формулировать на уровне «система должна поддерживать управление клиентами на узлах через внешний API», а не «система должна вызывать POST /api/inbounds/{id}/addClient».

### Перечень функциональных требований

#### Пользовательский контур

**Идентификация и доступ к системе:**

- Система должна обеспечивать идентификацию пользователя через мессенджер Telegram на основе уникального идентификатора чата.
- Система должна обеспечивать идентификацию пользователя через web-интерфейс на основе адреса электронной почты.
- Система должна позволять пользователю связать Telegram-аккаунт и web-аккаунт в единую учётную запись посредством одноразового токена с ограниченным сроком действия.

**Жизненный цикл доступа (пользовательская сторона):**

- Система должна позволять пользователю самостоятельно инициировать запрос на получение доступа.
- Система должна позволять пользователю однократно активировать пробный период без оплаты.
- Система должна обеспечивать пользователю получение конфигурации подключения по результатам успешного провижнинга.
- Система должна обеспечивать пользователю проверку текущего статуса подписки в любой момент.
- Система должна позволять пользователю самостоятельно инициировать продление подписки.

**Оплата:**

- Система должна поддерживать выбор пользователем тарифного плана и оформление оплаты.
- Система должна обеспечивать обработку подтверждения оплаты как основания для автоматической выдачи доступа.

> ⚠️ *Осторожная формулировка:* «Система должна поддерживать интеграцию с платёжным шлюзом» — не «Система интегрирована с платёжным шлюзом X». Конкретный шлюз в рамках ВКР — демонстрационный, боевая интеграция — за рамками.

#### Административный контур

**Управление заявками:**

- Система должна позволять администратору просматривать очередь поданных заявок на доступ.
- Система должна позволять администратору принимать решение по заявке (одобрение или отклонение) с обязательной фиксацией основания.

**Ручное управление доступом:**

- Система должна позволять администратору вручную выдавать доступ пользователю вне заявочного потока с фиксацией инициатора и основания.
- Система должна позволять администратору отзывать доступ пользователя с фиксацией причины и инициатора.
- Система должна позволять администратору блокировать учётную запись пользователя.

**Реестр и управление:**

- Система должна поддерживать ведение реестра предварительно одобренных субъектов, для которых выдача доступа производится без явной заявки.
- Система должна позволять администратору управлять тарифными планами: создавать, редактировать параметры, деактивировать.
- Система должна позволять администратору управлять промокодами: создавать с ограничениями по использованию, отслеживать применение.

**Аудит:**

- Система должна обеспечивать просмотр журнала операций с возможностью фильтрации по типу действия, субъекту и временному диапазону.

#### Автоматический контур

**Мониторинг и уведомления:**

- Система должна автоматически отслеживать приближение даты истечения подписки и направлять пользователю уведомление за установленный период до истечения.
- Система должна автоматически отслеживать расход трафика в рамках трафиково-ограниченной подписки.

**Автоматический отзыв:**

- Система должна автоматически отзывать доступ при истечении срока подписки.
- Система должна автоматически отзывать доступ при исчерпании трафиковой квоты.

**Провижнинг:**

- Система должна автоматически производить провижнинг клиентского доступа на серверном узле после наступления основания для выдачи (успешная оплата или одобрение заявки).

#### Интеграционный уровень

- Система должна поддерживать управление клиентами на серверных узлах через API внешней панели управления (node-level control-plane).
- Система должна поддерживать автоматизированное развёртывание серверных узлов через декларативное описание конфигурации.

> ⚠️ *Спорная формулировка:* «автоматизированное развёртывание» — это скорее нефункциональное/инфраструктурное требование. Если включать в 2.1.1, то только в интеграционную группу и без деталей реализации. Либо вынести в 2.7 как проектное решение с отсылкой к нефункциональному требованию воспроизводимости.

- Можно ли проверить каждое требование без знания архитектуры? → если нет, переформулировать или перенести в раздел 2.3.
- Не содержит ли формулировка названий классов, методов, таблиц БД? → если да, убрать.
- Каждое ли требование связано с конкретной проблемой главы 1? → если нет, обосновать или исключить.

## 3. Контекст для 2.1.2 «Нефункциональные требования»

### Принцип отбора

Включаются только те классы НФТ, которые:
1. прямо обусловлены контекстом ВКР (а не общими best practices);
2. влияют на проектные решения главы 2;
3. поддаются хотя бы качественной верификации в рамках задачи.

Не включаются: промышленный SLA, MTTF/MTTR, device posture, geographic redundancy, enterprise RBAC, высокая горизонтальная масштабируемость.

---

### Класс 1: Воспроизводимость развёртывания

**Почему важен:** добавление нового серверного узла — предусмотренный сценарий расширения топологии. Если развёртывание нельзя воспроизвести без ручных шагов, система не закрывает проблему инфраструктурного уровня, выявленную в анализе аналогов.

**Пересечение с ФТ:** нет. ФТ описывает, что можно сделать; это НФТ описывает, как это делается.

**Формулировка:**
- Повторный запуск процедуры развёртывания на уже настроенном узле не должен нарушать его работоспособное состояние (идемпотентность).

---

### Класс 2: Конфигурируемость без изменения кода

**Почему важен:** ВКР позиционирует систему как открытый продукт, пригодный к развёртыванию в разных окружениях. Если параметры зафиксированы в коде — каждая новая установка требует модификации исходников.

**Формулировка:**
- Все параметры, специфичные для окружения (адреса узлов, учётные данные, режимы работы), должны передаваться через переменные окружения и не фиксироваться в исходном коде.

---

### Класс 3: Управление функциональными блоками

**Почему важен:** у разных операторов могут быть разные наборы активных функций (реферальная программа, режим заявок, режим обслуживания). Пересборка образа ради включения/отключения функции — неприемлемые операционные издержки.

**Формулировка:**
- Система должна поддерживать активацию и деактивацию отдельных функциональных блоков через конфигурацию без пересборки компонентов.

---

### Класс 4: Расширяемость топологии

**Почему важен:** прямое следствие из требования поддержки нескольких узлов доступа (глава 1.2, многоузловая топология). Если добавление нового узла требует изменения кода — это архитектурный дефект, противоречащий цели системы.

**Формулировка:**
- Добавление нового серверного узла доступа не должно требовать изменения исходного кода — только изменения конфигурации и повторного развёртывания.

---

### Класс 5: Устойчивость пользовательского контура

**Почему важен:** 3x-ui — внешняя система, её временная недоступность не должна приводить к неработоспособности всей системы. Пользователи в этом случае должны получать понятный ответ, а не необработанную ошибку.

**Формулировка:**
- При временной недоступности внешней панели управления узлом система должна выполнять повторные попытки запроса с задержкой, не завершая работу аварийно, и информировать пользователя о временной недоступности операции.

---

### Класс 6: Независимость компонентов при развёртывании

**Почему важен:** монорепозиторий не означает монолит. Backend, telegram_bot и frontend должны запускаться и обновляться независимо. Это снижает риск каскадного отказа при обновлении одного компонента.

**Формулировка:**
- Каждый компонент системы должен допускать независимое развёртывание и обновление без остановки остальных компонентов.

---

### Класс 7: Аудируемость (наблюдаемость операций)

**Почему важен:** один из двух главных аргументов в пользу системы относительно аналогов — прослеживаемость жизненного цикла доступа. Если это только ФТ, теряется инженерный смысл. Как НФТ это требование к качеству журналирования.

**Граница с ФТ:** ФТ — «Система должна позволять просматривать журнал». НФТ — «Каждое административное действие должно фиксироваться с атрибутами: субъект, действие, объект, время, основание».

**Формулировка:**
- Каждое административное действие и каждое автоматическое изменение статуса доступа должны фиксироваться в журнале с указанием субъекта, типа действия, объекта воздействия, временной метки и основания.

---

### Класс 8: Безопасность в пределах рамки задачи

**Почему важен:** система обрабатывает персональные данные (email, Telegram ID) и управляет доступом. Минимальный набор требований безопасности необходим.

**Что включать:** хранение паролей только в хэшированном виде, токены с ограниченным сроком жизни, путь административной панели не предсказуем по умолчанию.

**Что не включать:** device posture, MFA, enterprise PKI — за рамками задачи.

**Формулировки:**
- Система не должна хранить пароли пользователей в открытом виде.
- Токены, используемые для аутентификации и связывания учётных записей, должны иметь ограниченный срок действия.

> ⚠️ *Не формулировать как «Система обеспечивает безопасность данных» — это декларация, а не требование. Только конкретные, проверяемые утверждения.*

## 4. Контекст для 2.1.3 «Проектные ограничения и допущения»

### Зачем нужен этот подпункт

Без явного перечня ограничений рецензент вправе задать вопрос: «Почему система не поддерживает X?» — и не найти ответа в тексте. Это создаёт впечатление упущений, тогда как речь идёт об осознанных решениях.

Ограничения — это не признание недостатков. Это инженерная честность: система решает задачу в определённых границах, и границы явно обозначены. Академический текст выигрывает от этого: он выглядит обоснованным, а не расплывчатым.

### Как не превратить ограничение в признание слабости

Плохо: «Система не поддерживает MFA, что снижает уровень безопасности».
Хорошо: «Многофакторная аутентификация и проверка состояния клиентского устройства выходят за рамки задачи настоящей работы: система идентифицирует субъекта, но не верифицирует устройство. Включение этих механизмов потребовало бы интеграции с внешними Identity-провайдерами, что является самостоятельной задачей.»

Формула: **«X не входит в рамки работы, потому что Y»** — не «X реализовать не удалось».

### Перечень ограничений и допущений

#### 1. Отсутствие многофакторной аутентификации и device posture

**Зачем фиксировать:** идентификация пользователя через Telegram ID или email — достаточна для задачи управления доступом в контексте ВКР, но не соответствует enterprise-требованиям строгой аутентификации.

**Формулировка:** Многофакторная аутентификация и проверка состояния клиентского устройства (device posture) не входят в рамки настоящей работы. Система идентифицирует субъекта по каналу обращения (Telegram ID или адрес электронной почты), но не проверяет состояние устройства при каждом обращении.

---

#### 2. Упрощённая ролевая модель

**Зачем фиксировать:** система разграничивает только два уровня — пользователь и администратор. Гранулярный RBAC (разграничение прав внутри административного уровня) не проектируется.

**Формулировка:** Ролевая модель системы включает два уровня: пользователь и администратор. Разграничение прав внутри административного уровня (гранулярный RBAC) не является предметом настоящей работы.

---

#### 3. Зависимость от 3x-ui как внешнего node-level control-plane

**Зачем фиксировать:** система взаимодействует с конкретным API 3x-ui; это не произвольная технология, а обоснованный выбор (глава 1 анализ аналогов). Но это означает, что смена или добавление другого control-plane потребует доработки.

**Формулировка:** В рамках настоящей работы в качестве node-level control-plane используется только панель управления 3x-ui. Поддержка панелей с иным API не предусматривается. Интеграция с дополнительными control-plane является перспективным направлением развития системы.

---

#### 4. Отсутствие боевой интеграции с платёжным шлюзом

**Зачем фиксировать:** платёжный цикл спроектирован и реализован, но конкретный шлюз — демонстрационный. Боевая интеграция требует коммерческого договора и верификации, что выходит за рамки учебной разработки.

**Формулировка:** Интеграция с платёжным шлюзом предусмотрена на уровне архитектуры: система поддерживает обработку webhook-уведомлений об успешной оплате. В рамках настоящей работы используется демонстрационный шлюз, эмулирующий успешную оплату. Подключение конкретного коммерческого шлюза не является предметом разработки.

---

#### 5. Отсутствие горизонтального масштабирования сервисного уровня

**Зачем фиксировать:** backend проектируется для однонодового развёртывания. Требование горизонтального масштабирования не поставлено — его включение потребовало бы решения проблем согласованности состояния в распределённой среде, что является отдельной задачей.

**Формулировка:** Горизонтальное масштабирование сервисного уровня (несколько инстанций backend) не предусматривается. Сервисный уровень развёртывается как единственная инстанция; задача обеспечения согласованности состояния при распределённом развёртывании выходит за рамки настоящей работы.

---

#### 6. Отсутствие собственной реализации VPN- или proxy-протокола

**Зачем фиксировать:** тема ВКР — управляющий сервис, не новый протокол. Это нужно зафиксировать явно, чтобы читатель не ожидал реализации транспортного уровня.

**Формулировка:** Система не реализует VPN- или proxy-протокол. Передача трафика обеспечивается существующими компонентами Xray-core на серверных узлах; разрабатываемый сервис управляет жизненным циклом доступа, но не участвует в маршрутизации пользовательского трафика.

---

#### 7. Telegram как основной, но не единственный пользовательский канал

**Зачем фиксировать:** позиционирование бота как «интерфейса управления» (тема ВКР) должно быть уточнено. Telegram — основной пользовательский канал; web — параллельный. Административный канал — web.

**Формулировка:** Telegram-бот проектируется как основной пользовательский интерфейс для операций самообслуживания. Административные функции сосредоточены в web-интерфейсе. Использование Telegram в качестве единственного канала не предполагается: web-кабинет обеспечивает параллельный доступ ко всем пользовательским операциям.

## Дополнительные замечания для автора

1. **Не начинать раздел с тезиса «требования сформированы на основе анализа»** — это самоочевидно и выглядит как заполнение объёма. Лучше сразу показать логику первым предложением.

2. **Избегать слова «система» в каждом предложении подряд** — это монотонно. Чередовать с конкретными формулировками субъекта: «пользователь должен иметь возможность», «администратор должен получать», «автоматический процесс должен...».

3. **Не использовать «гарантирует», «полностью обеспечивает», «исключает» без оговорок** — в академическом тексте это либо верифицируется, либо звучит как реклама.

4. **Подпункт 2.1.3 писать не как извинение, а как инженерное решение** — «X не входит в рамки» всегда сопровождается «потому что Y», где Y — содержательное обоснование.

5. **Нефункциональные требования не должны превращаться в перечень «хороших свойств»** — каждое связано с конкретным проектным решением в разделах 2.3–2.7.
