## 2. Понятийная база (подраздел 1.1)

### Ключевое разграничение — центральное для всей главы

- **Data-plane (канал/протокол/туннель/relay):** устанавливает защищённое соединение, шифрует или инкапсулирует трафик, реализует передачу данных между клиентом и узлом. Не хранит бизнес-состояние доступа, не принимает решения «кому/когда/на каких условиях».
- **Access-management service (сервис управления доступом):** принимает решения о выдаче доступа, хранит состояние (пользователи, сроки, лимиты, статусы, основания), инициирует техническое применение доступа в control-plane узла, предоставляет интерфейсы пользователю и администратору, ведёт журнал.
- **Node-level control-plane (панель/контроллер узла):** управляет конфигурационным состоянием конкретного узла: создаёт/удаляет клиентов, inbound-правила, лимиты, subscription links. Отдельный слой между data-plane и access-management service.

Это разграничение нормативно обосновано: NIST SP 800-207 явно описывает разделение control plane и data plane и вводит компоненты Policy Engine/Administrator (принимают решение доступа) и Policy Enforcement Point (исполняют) [NIST SP 800-207, https://csrc.nist.gov/pubs/sp/800/207/final].

**Вывод для ВКР:** разрабатывается не новый VPN- или proxy-протокол, а access-management service — интегрирующий слой, автоматизирующий жизненный цикл доступа поверх существующего узла (3x-ui/Xray).

### Рабочие определения (компактные, операциональные)

| Понятие | Определение | Нормативная/техническая база |
|---|---|---|
| Защищённый удалённый доступ | Доступ пользователя к системе через внешнюю сеть с применением механизмов аутентификации, авторизации, защиты канала и операционного контроля (жизненный цикл, отзыв, аудит). | NIST Glossary: remote access — доступ к org. системе через внешнюю сеть; NIST SP 800-46 Rev. 2. |
| VPN | Механизм data-plane, создающий защищённое виртуальное соединение. Распределение ключей и управление правами доступа — отдельный слой; WireGuard явно описывает обмен публичными ключами «out-of-band». | WireGuard paper (NDSS 2017); RFC 4301 (IPsec tunnel mode SA). |
| Proxy | Посредник, пересылающий запросы между клиентом и ресурсом. HTTP proxy — «message-forwarding agent»; SOCKS5 — «shim-layer between application and transport». | RFC 9110 (HTTP proxy); RFC 1928 (SOCKS5). |
| ZTNA | Архитектурный подход, при котором доступ предоставляется не по факту нахождения в сети, а по результатам проверки субъекта, устройства и контекста. Использовать как ориентир, не как «замену VPN». | NIST SP 800-207. |
| Туннель | Логический инкапсулированный канал; в защищённом варианте включает криптографическую защиту и применение политик. | RFC 4301: tunnel mode SA как «SA applied to an IP tunnel». |
| Control-plane | Уровень управления, хранящий конфигурационное состояние и политики; используется для управления каналами доступа, а не для передачи пользовательского трафика. | NIST SP 800-207: отделение control plane от data plane. |
| Data-plane | Уровень, по которому идёт реальный трафик пользователя после предоставления доступа. | NIST SP 800-207. |
| Жизненный цикл доступа | Последовательность операций и состояний: запрос/инициирование → решение → техническая выдача → доставка → мониторинг → продление → отзыв → аудит. | Подтверждается моделями `AccessRequest`, `AccessGrant`, `AccessRegistryEntry`, `AdminAuditLog` в репозитории. |

> **Терминологическая заметка:** избегать «транспортный уровень» без оговорки, что это data-plane в архитектурном смысле, а не OSI Layer 4.

## 3. Жизненный цикл доступа — детализация (подраздел 1.2)

Базис для сравнения аналогов в 1.3. Минимальный набор операций:

| № | Операция | Что происходит | Риски при ручной организации |
|---|---|---|---|
| 1 | Идентификация и связывание | Пользователь регистрируется; web-аккаунт связывается с Telegram ID. Без этого нельзя гарантировать корректную доставку конфигурации и аудит. | Дубли пользователей; отсутствие связи между каналами; неправильный получатель конфигурации. |
| 2 | Запрос/инициирование доступа | Пользователь подаёт заявку, приобретает план или получает приглашение. | Запросы теряются; нет единой очереди; зависимость от доступности администратора. |
| 3 | Принятие решения | Автоматическая проверка по политике или ручное одобрение; результат и основание фиксируются. | Нет записи основания; одобрение устно/в чате; нельзя воспроизвести историю решения. |
| 4 | Техническая выдача доступа | Создание/обновление клиента в node-level control-plane (панели/API), назначение лимитов, сроков, inbound. | Ошибка в параметрах; ручной выбор inbound; несогласованность с доменным реестром. |
| 5 | Доставка конфигурации | Пользователь получает ссылку/QR/файл конфигурации; подтверждение доставки. | Использование незащищённых каналов; потеря ссылки; нет статуса доставки. |
| 6 | Мониторинг срока/лимитов | Отслеживание времени истечения и трафикового лимита; уведомления за N дней. | Просроченные доступы активны; пользователь не предупреждён; реестр не синхронизирован с панелью. |
| 7 | Продление/изменение | Продление срока или лимита, синхронизация с панелью, запись основания. | Несогласованность между оплатой и фактическим сроком; нет истории продлений. |
| 8 | Отзыв/деактивация | Удаление или деактивация клиента на узле; запись причины и инициатора. | Клиент остаётся активным на части узлов; причина не фиксируется. |
| 9 | Журналирование | Сохранение всех операций: кто, что, когда, почему, с каким результатом. | Без журнала невозможно восстановить цепочку; администратор опирается на переписку. |

**Опора:** «manual orchestration and configuration of network security functions is no more feasible» — Bringhenti et al., ACM Computing Surveys, 2023, doi:10.1145/3616401.

### Участники (акторы) — использовать стабильно по всей ВКР

- **Пользователь** — субъект, получающий доступ, работающий в режиме self-service.
- **Администратор/оператор** — субъект управления, утверждающий исключения, несущий ответственность.
- **Access-management service** (разрабатываемый backend) — источник истины доменного состояния.
- **Node-level control-plane** (3x-ui, Xray-панель) — место технического применения доступа.
- **Data-plane узла** (Xray-core) — место передачи пользовательского трафика.
- **Внешние контуры** — платежи, уведомления, email, журналирование.

## 4. Проблемы ручного управления (подраздел 1.2 — содержание)

Формулировать не как «неудобства», а как системные свойства ручного процесса:

- **Неустранимый человеческий фактор.** Ручная выдача состоит из множества мелких операций (шаблон, клиент, срок, ссылка, отправка, запись). Ошибка в любой из них — неправильный срок, неверный получатель, нерабочая конфигурация, пропуск в реестре.

- **Отсутствие единого реестра.** Состояние доступа распределено между панелью, таблицей и перепиской. При продлении и отзыве возникает несогласованность: локальная запись изменена, клиент на панели — нет.

- **Зависимость пользователя от доступности администратора.** Каждый шаг самообслуживания (статус, конфигурация, продление, заявка) требует обращения к администратору. При росте числа пользователей это становится узким местом.

- **Риски при передаче конфигурации.** Конфигурации содержат чувствительные параметры. Ручная передача через несистемные каналы создаёт риск утечки, ошибочного получателя, потери инструкции.

- **Ограниченная масштабируемость.** При росте числа пользователей линейно растёт нагрузка на администратора — не только по первичным выдачам, но и по повторным операциям: напоминания, продления, повторные запросы, смена узла.

- **Разрыв между инфраструктурным и пользовательским уровнями.** Панель управляет клиентами и техническими сроками, но пользовательский процесс включает заявку, основание, оплату, уведомления, историю и поддержку. Без интегрирующего слоя администратор сам становится таким слоем.

## 5. Классификация существующих решений (подраздел 1.3)

### ⚠️ Исправления по сравнению с предыдущей версией контекста

1. **3x-ui HAS a documented API.** Официальная Wiki 3x-ui содержит раздел «API Documentation» с описанием аутентификации (`/login`), базовым путём (`/panel/api/inbounds`), операциями `addClient / updateClient / delClient`. Нельзя писать «без документированного API». Корректный тезис: *API существует и задокументирован, но Telegram-бот 3x-ui ориентирован на уведомления и админ-функции панели, а не на пользовательский self-service цикл*.

2. **OpenVPN Access Server HAS a Client Web UI.** Официальная документация описывает Client Web UI, через который пользователи входят и скачивают преднастроенный клиент или профиль .ovpn. Нельзя писать «нет пользовательского канала». Корректный тезис: *пользовательский web-канал есть, но он не включает Telegram-интерфейс, управление заявками и продуктовый жизненный цикл подписки*.

3. **Нельзя утверждать «нет open-source решений, объединяющих X+Y+Z».** Существуют проекты, позиционирующие себя как bot + backend + web cabinet (Bedolaga, AltShop, VPNMarket). Корректный тезис: *существующие решения фрагментированы по уровням и продуктовому замыслу; unified access-management service с явной моделью заявок/оснований/аудита и IaC-развёртыванием как единый инженерный контур не представлен*.

4. **VPNMarket лицензирован как MIT** (заявлено в репозитории) — исправить строку в таблице.

5. **HolderBot — проблема лицензии.** На странице репозитория лицензия явно не отображается. Использовать осторожно, только как функциональный аналог бот-интерфейса.

### Классы решений

**Класс A: Data-plane технологии (протоколы/демоны/relay)**

Роль: передача трафика, криптографическая защита, маршрутизация.
Ключевое свойство: управление пользователями и жизненным циклом — вне их зоны ответственности; требуется внешний инструмент.

| Решение | Особенность | Роль в ВКР |
|---|---|---|
| WireGuard | Протокол туннелирования (<4000 строк кода ядра); ключи распределяются «out-of-band» | Эталон data-plane протокола; демонстрирует разрыв между туннелем и управлением |
| OpenVPN Community | Зрелый VPN-протокол, гибкая конфигурация | Фоновый контекст класса |
| Xray-core | Многопротокольный proxy/relay движок (Vless, Vmess, Trojan, Shadowsocks, WireGuard) | Data-plane узла в разрабатываемой системе |

---

**Класс B: Node-level control-plane панели**

Роль: управление конфигурацией узла — клиенты, inbound-правила, лимиты трафика, сроки, subscription links, статистика, иногда API и уведомления.
Ключевое свойство: ориентированы на административный контроль узла; пользовательский self-service жизненного цикла (заявки/основания/аудит/продления через единый канал) закрывают частично или не закрывают.

| Решение | API | Telegram-бот | Пользовательский канал | Лицензия |
|---|---|---|---|---|
| **3x-ui** | Документирован в Wiki (`/panel/api/inbounds`, addClient/updateClient/delClient) | Есть; ориентирован на уведомления трафика/истечения и админ-операции панели | Client web UI отсутствует; пользователь получает ссылку через администратора | GPL-3.0 |
| **Marzban** | REST API + webhooks, документированы | Есть; заявлены multi-admin, subscription links | Subscription links как пользовательский канал; степень self-service — уточнить по docs | AGPL-3.0 |
| **Remnawave Panel** | REST API | Отдельно (экосистема) | Отдельный web cabinet (экосистема) | AGPL-3.0 |
| **wg-easy** | API существует; документация помечает endpoints как «not yet documented» / изменяемые | Нет | Нет | MIT |
| **Outline Server (Jigsaw/Google)** | REST Management API для access keys (создание/удаление/ротация) | Нет | Outline Manager (desktop) для администратора; нет user self-service | Apache-2.0 |
| **OpenVPN Access Server** | OpenAPI (Swagger) с версии 3.0; операции над аккаунтами, профилями, сертификатами | Нет | **Client Web UI есть** — пользователь скачивает профиль/клиент | Коммерческая |

---

**Класс C: Service-level «commerce/lifecycle» слои — прямые аналоги**

Роль: Telegram-бот + backend + (иногда) web cabinet поверх панели класса B; закрывают часть жизненного цикла: подписка/оплата/промокоды/выдача/уведомления.
Ключевое свойство: наиболее близкие аналоги по замыслу; важно проверить покрытие lifecycle-чеклиста и лицензию.

| Решение | Описание | Lifecycle-покрытие | Лицензия | Статус |
|---|---|---|---|---|
| **3xui-shop** | Telegram bot для продаж, использует API 3x-ui | Покупка → выдача → уведомления; аудит/заявки — не описаны | Не указана | Архивирован (read-only) |
| **remnashop** | Telegram bot для продаж, интеграция с Remnawave | Подписки/оплата; lifecycle — уточнить по docs | MIT | Активен |
| **AltShop** | Telegram bot + FastAPI backend + web portal; admin-контроль в Telegram | Покупка/выдача/продление/web-портал; audit trail — уточнить | Уточнить | Активен |
| **Bedolaga Bot & Cabinet** | Telegram bot + web cabinet (официальная документация); позиционируется как full lifecycle + payments через Remnawave | Заявлены подписки/оплата/web-кабинет; глубину заявок/аудита — верифицировать по docs | Уточнить | Активен |
| **VPNMarket** | Panel + automated sales Telegram bot; Marzban & 3x-ui | Продажи/выдача; audit/заявки — уточнить | MIT (заявлено в репозитории) | Активен |
| **HolderBot** | Multi-panel VPN bot; 3x-ui значится среди supported panels | Частичный lifecycle; степень — уточнить | ⚠️ Лицензия не отображается явно | Активен |

> **Принцип для таблицы сравнения в 1.3:** помечать «подтверждено в docs/репозитории» vs «не описано/не подтверждено». Не приписывать функции на основании README без проверки.

---

**Класс D: Корпоративные ZTNA и overlay-платформы**

Роль: identity-based доступ к приложениям/ресурсам; иная модель эксплуатации.
В ВКР — фоновый класс, обозначающий границу предметной области. Не смешивать с «выдачей VPN/proxy-конфигураций через Telegram».

Примеры: Cloudflare Zero Trust/Access, Tailscale, Firezone, NetBird, Headscale.

---

### Функциональные роли — итог

| Уровень | Кто отвечает | Классы |
|---|---|---|
| Data-plane (передача трафика) | Протоколы/демоны/relay | A |
| Node-level control-plane (конфигурация узла) | Панели управления | B |
| Service-level lifecycle (управление жизненным циклом) | Commerce/lifecycle слои | C |
| Enterprise governance | ZTNA/overlay-платформы | D |

**Разрабатываемая система** — класс C, но с отличиями: явная модель заявок/оснований, общий доменный слой (`shared`), IaC-развёртывание (Ansible), web-кабинет как полноценный параллельный канал, не зависящий от Telegram.

## 6. Критерии сравнения (для таблицы подраздела 1.3)

| # | Критерий | Что оценивается | Почему важен |
|---|---|---|---|
| 1 | **Покрытие жизненного цикла доступа** | Какие операции из чеклиста (запрос → решение → техническая выдача → доставка → мониторинг → продление → отзыв → аудит) реализованы как управляемый процесс | Это предмет ВКР — не протокол, а сервис управления |
| 2 | **Интеграционная поверхность control-plane** | Наличие и стабильность API, webhooks, спецификации для автоматизации технического управления доступом | Разрабатываемый сервис должен программно управлять узлом доступа |
| 3 | **Пользовательский канал** | Какие операции доступны пользователю самостоятельно (Telegram / web / subscription link) и что требует участия администратора | Обосновывает выбор Telegram-бота и web-кабинета |
| 4 | **Административный канал** | Наличие ролей, web-интерфейса/CLI, возможности ручного управления и аудита для администратора | Необходим для контроля и обработки исключений |
| 5 | **Управляемость состояния и аудит** | Единый реестр выдач/статусов, трассировка «кто/что/когда/почему», согласованность между доменным реестром и фактическим состоянием узла | Ручной процесс не обеспечивает проверяемости и воспроизводимости |
| 6 | **Воспроизводимость развёртывания** | IaC (Ansible/Terraform), контейнеризация, документированный deployment | ВКР явно включает автоматизированное развёртывание как задачу |
| 7 | **Лицензия и модифицируемость** | Лицензия явно определена и совместима с использованием, изучением и изменением | Open-source позиционирование системы; закрытые платформы нишу не закрывают |

> Deployment и лицензия — ограничения/свойства, а не «функции» в одном ряду с lifecycle.

## 7. Формулировка системного разрыва (подраздел 1.4 / 1.5)

### Что корректно утверждать

Существующие решения **фрагментированы по уровням и продуктовому замыслу**:

- Классы A и B (протоколы и панели) хорошо закрывают data-plane и node-level control-plane, но не предоставляют service-level управления жизненным циклом с единым реестром, моделью заявок/оснований и аудитом.
- Класс C (commerce/lifecycle слои) закрывает значительную часть сценария «бот + продажи», но большинство решений тесно привязаны к конкретной панели, не предоставляют IaC-развёртывания как части системы, а модель заявок/оснований и полноценный audit trail в публичных docs описаны неполно или не описаны вовсе.
- Класс D (ZTNA) — иная модель доступа, не применима напрямую для self-hosted выдачи proxy/VPN-конфигураций через Telegram.

### Что нельзя утверждать без уточнения условий

- «Нет open-source решений, объединяющих X+Y+Z» — **неверно без условий**: AltShop, Bedolaga, VPNMarket существуют.
- «3x-ui не имеет API» — **фактически неверно**.
- «OpenVPN AS не имеет пользовательского канала» — **неточно** (Client Web UI существует).
- «ZTNA полностью заменяет VPN» — в рамках NIST SP 800-207 корректнее «иная парадигма», а не «замена».

### Рекомендуемая формулировка вывода

> Большинство решений либо управляют технической настройкой доступа на уровне узла, не закрывая service-level lifecycle и governance (заявки/основания/аудит/единый реестр), либо предоставляют Telegram commerce flow, зависящий от внешней панели и не гарантирующий unified domain registry и IaC-развёртывание в одном инженерном контуре. Это обосновывает разработку специализированного access-management service, интегрирующего указанные слои.

## 8. Обоснование Telegram-бота и web-панели (подраздел 1.4)

### Что обосновано корректно

- Telegram Bot API поддерживает long polling, webhook, slash-команды, inline-клавиатуры, callback-запросы — достаточно для реализации событийных сценариев: уведомления, подтверждения, получение ссылки, статус, короткие action flows. [Telegram Bot API, core.telegram.org/bots/api]
- Пользователю не нужно устанавливать отдельное приложение сервиса.

### Что нужно добавить для полноты обоснования

- Telegram-интерфейс рационален для **оперативных событийных сценариев**, но ограничен для задач с большим массивом данных, сложными фильтрами, массовыми операциями — это обосновывает web-кабинет как параллельный канал.
- AltShop как аналог демонстрирует, что «административный контроль в Telegram» — рабочая практика, а web-часть используется как портал для пользователей.

### Ограничения канала (упомянуть в тексте как осознанные)

- Компрометация Telegram-аккаунта требует строгого связывания Telegram ID с доменной учётной записью.
- Риск утечки конфигурации при пересылке сообщений — снижается явной привязкой доставки к верифицированной учётной записи.
