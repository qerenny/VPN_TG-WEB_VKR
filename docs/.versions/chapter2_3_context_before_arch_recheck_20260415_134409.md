# chapter2_3_context.md

## 1. Логика архитектурного проектирования

Подраздел 2.3 нужен для перехода от требований и сценариев к общей структуре системы. Если 2.2 отвечает на вопрос «кто и что делает», то 2.3 фиксирует, какие подсистемы обеспечивают эти действия, как между ними распределена ответственность и через какие связи они взаимодействуют.

Рабочая логика:

```text
требования и процессы предметной области -> архитектурные уровни -> подсистемы -> связи между ними
```

Архитектуру нельзя описывать как простой перечень папок. Репозиторий действительно разделён на `backend/`, `telegram_bot/`, `frontend/`, `shared/`, `ansible/`, но архитектурный смысл появляется только после сопоставления этих частей с уровнями ответственности: пользовательское и административное взаимодействие, сервисное управление жизненным циклом доступа, хранение доменного состояния, интеграция с node-level control-plane, инфраструктурное развёртывание.

Связь с главой 1 должна быть прямой. Там зафиксирован разрыв между data-plane, control-plane узла и сервисным управлением доступом. Поэтому в 2.3 важно показать, что разрабатываемая система не создаёт новый VPN/proxy-протокол и не становится точкой маршрутизации трафика. Она проектируется как сервисный координирующий слой, который хранит состояние доступа, предоставляет пользовательские и административные каналы, инициирует технический провижнинг через 3x-ui API и поддерживает инфраструктурный контур развёртывания.

Граница между архитектурным решением и реализационной деталью проходит по уровню обобщения. Утверждение «backend и telegram_bot выполняются как отдельные процессы и используют общие PostgreSQL/Redis» относится к архитектуре. Указание конкретного метода, endpoint, SQL-запроса или класса очереди — уже материал главы 3. Исключение допустимо только для краткой верификации факта по проекту, но не для раскрытия реализации.

## 2. Контекст для архитектурных уровней

### Инфраструктурный уровень

Назначение: подготовка узлов и окружения, в котором работают сервисные компоненты и node-level control-plane. В проекте подтверждается папкой `ansible/`: роли `server_baseline`, `certbot_setup`, `nginx_proxy`, `xui_app`, `bot_server`, `migration_manager`; playbook `site.yml` разворачивает X-UI/3x-ui, Nginx, сертификаты и миграционный контур для узлов доступа, `bot_server.yml` готовит хост приложения с Docker/Nginx.

Входит в предмет проектирования ВКР как инфраструктурный контур, но детали развёртывания лучше вынести в 2.7. В 2.3 достаточно показать, что инфраструктурный уровень обеспечивает воспроизводимость и отделён от бизнес-логики.

### Data-plane

Назначение: передача пользовательского трафика после выдачи доступа. В контексте проекта это уровень Xray/прокси-узла, поднимаемый и обслуживаемый вне прикладных компонентов. Прямой реализации data-plane в `backend/`, `telegram_bot/`, `frontend/` или `shared/` не обнаружено.

Этот уровень используется как внешняя основа. Разрабатываемая система не должна описываться как система маршрутизации трафика, DPI, сетевой экран или собственный VPN/proxy-протокол. Смешение data-plane с сервисным уровнем методически неверно: оно подменяет задачу управления жизненным циклом доступа задачей передачи сетевого трафика.

### Node-level control-plane

Назначение: техническое управление клиентами, inbound, сроками и лимитами на узле. В проекте таким уровнем выступает 3x-ui API. Это подтверждается конфигурационными группами `SERVERS__...`, `TRAFFIC_LIMITED_SERVERS__...`, функциями построения URL к `/panel/api/inbounds/` и модулем `telegram_bot/infrastructure/api`, где реализованы HTTP-вызовы к панели.

3x-ui API является внешней системой. Проектируемый сервис обращается к нему для провижнинга и синхронизации, но не заменяет панель управления узлом и не описывает её внутреннюю архитектуру.

### Сервисный уровень

Назначение: управление доменным жизненным циклом доступа. В проекте этот уровень представлен `backend/`, `telegram_bot/`, `frontend/` и общим слоем `shared/`. Он хранит пользователей, заявки, выданные доступы, подписки, платежные события, реестр разрешений и аудит; предоставляет web API, Telegram-сценарии и web-интерфейс; использует PostgreSQL и Redis как инфраструктурные зависимости.

ВКР проектирует именно этот уровень и его связи с инфраструктурным контуром и 3x-ui API. Нельзя смешивать его с node-level control-plane: сервис решает, кому и на каких условиях выдать доступ, а 3x-ui применяет техническую конфигурацию на узле.

## 3. Контекст для состава подсистем, их взаимодействия и границ ответственности

### Фактически подтверждённые подсистемы

| Подсистема | Архитектурная роль | Подтверждение по проекту |
|---|---|---|
| `backend/` | Сетевой API сервис: web-аутентификация, пользовательский кабинет, admin API, public config, subscription endpoints, payment webhook | `backend/main.py`, router-группы `auth`, `me`, `admin`, `payments`, `subscription`, Dockerfile, compose-сервис `backend` |
| `telegram_bot/` | Процесс Telegram-бота и фоновых задач: polling, пользовательские сценарии, уведомления, обработка оплат, lifecycle/sync workers, интеграция с 3x-ui | `telegram_bot/main.py`, `bootstrap.py`, presentation/services/infrastructure, compose-сервис `telegram_bot` |
| `frontend/` | Статическое Vue-приложение: web-кабинет, admin panel, публичные страницы subscription/config | `frontend/package.json`, `router/index.ts`, `src/api/*`, Dockerfile, compose-сервис `frontend` как extractor/builder |
| `shared/` | Общий Python-пакет: конфигурация, модели SQLModel, репозитории, сервисы доступа, Alembic-миграции, утилиты | `shared/pyproject.toml`, `shared/src/shared`, `shared/alembic`, Dockerfile `shared/alembic/Dockerfile` |
| `ansible/` | Инфраструктурный контур подготовки узлов и хостов | playbooks и roles для X-UI, Nginx, Certbot, Docker-host, migration |
| PostgreSQL | Основное хранилище доменного состояния | `docker-compose*.yml`, `shared/config/database/engine.py`, модели и миграции |
| Redis | Кэш, очереди и координация фоновых задач | `docker-compose*.yml`, ключи `REDIS_*`, queue services, backend lifespan |
| 3x-ui API | Внешний node-level control-plane | `ClientManager`, `APIConnection`, server config templates |
| Платёжный шлюз | Внешний источник события оплаты; в проекте подтверждён generic webhook и demo gateway | `payment_webhook_routes.py`, `demo_payment_gateway.py`, payment services |

### Архитектурно значимые связи

- `frontend -> backend`: синхронное HTTP-взаимодействие через Axios, базовый адрес задаётся `VITE_API_URL`. Это основной web-канал для пользователя и администратора.
- `backend -> PostgreSQL`: прямой доступ через общий `shared`-слой, SQLModel/SQLAlchemy и `get_db_session`.
- `telegram_bot -> PostgreSQL`: прямой доступ через тот же `shared`-слой. Следствие: доменное состояние общее, а не синхронизируется между двумя независимыми БД.
- `backend -> Redis`: кэш subscription-ответов, admin/session-support, постановка оплаченных webhook-событий в очередь при доступном Redis.
- `telegram_bot -> Redis`: очереди напоминаний и payment fulfillment; используются ready/retry/dead-letter очереди.
- `backend/telegram_bot -> 3x-ui API`: HTTP-интеграция с внешней панелью. Важно: интеграция используется не только ботом; backend также импортирует `ClientManager` и сервисы из `telegram_bot` для административных и web-сценариев. Поэтому нельзя утверждать строгую кодовую независимость backend от bot-пакета.
- `telegram_bot -> Telegram Bot API`: long polling и отправка сообщений. В 2.3 это внешняя связь сервиса, а не предмет интерфейсного проектирования.
- `backend <- платёжный webhook`: синхронный входящий HTTP-запрос, после которого платёжное событие может быть поставлено в Redis-очередь для асинхронной обработки бот-процессом.
- CI/CD -> контейнерные образы: GitHub Actions собирает и публикует образы `backend`, `telegram_bot`, `alembic`, `frontend`, а production compose использует эти образы. Это подтверждает контур поставки, но на компонентной диаграмме раздела 2.3 его лучше не показывать как runtime-компонент.

### Границы ответственности

Разрабатываемый сервис отвечает за сервисное состояние доступа, пользовательские и административные сценарии, интеграцию с 3x-ui API, хранение истории и координацию фоновых процессов. Он не реализует собственный VPN/proxy-протокол, не является data-plane, не передаёт пользовательский трафик и не должен описываться как система сетевой маршрутизации.

3x-ui остаётся внешним control-plane узла. Ansible может подготавливать инфраструктуру и устанавливать/настраивать этот уровень, но бизнес-решения о доступе принимаются в сервисном слое. PostgreSQL и Redis являются инфраструктурными зависимостями, а не самостоятельными предметными подсистемами.

Отдельное ограничение: по файлам подтверждается runtime-разделение backend и telegram_bot на разные контейнеры, но не подтверждается полная кодовая изоляция. Backend зависит от `telegram_bot` как локального Python-пакета и использует часть его сервисов. В тексте 2.3 это лучше формулировать как «раздельные исполняемые компоненты с общим кодовым слоем и общей БД», а не как полностью независимые микросервисы.

## 4. Контекст для компонентной диаграммы и архитектурных выводов раздела

Для 2.3 нужна одна UML Component диаграмма. Внутри границы «Разрабатываемый сервис» целесообразно показать `backend`, `telegram_bot`, `frontend`, `shared` и `alembic`/миграционный компонент. `shared` лучше отразить как общий библиотечный/доменный слой, используемый backend, bot и alembic, а не как отдельный сетевой сервис. `ansible` лучше вынести в отдельный блок «Инфраструктурный контур», связанный с узлом 3x-ui и хостом приложения; не помещать его внутрь runtime-приложения.

Внешние системы на диаграмме: PostgreSQL, Redis, 3x-ui API, Telegram Bot API, платёжный шлюз. Опционально можно показать GitHub Actions/GHCR как контур поставки, но только если диаграмма не перегружается; для runtime-архитектуры это второстепенно.

Связи, которые стоит показать:

- `frontend -> backend`: HTTP/REST.
- `backend -> PostgreSQL`, `telegram_bot -> PostgreSQL`, `alembic -> PostgreSQL`.
- `backend -> Redis`, `telegram_bot -> Redis`.
- `backend -> 3x-ui API` и `telegram_bot -> 3x-ui API` как внешняя HTTP-интеграция.
- `telegram_bot -> Telegram Bot API`.
- `платёжный шлюз -> backend`: webhook.
- `backend`, `telegram_bot`, `alembic` используют `shared`.

Детали, которые лучше оставить вне диаграммы: конкретные router-группы, endpoint, таблицы БД, названия Redis-ключей, внутренние service-классы, handlers, Vue-компоненты, отдельные Ansible tasks. Иначе component diagram превратится в смесь sequence diagram, deployment diagram и файлового дерева.

Архитектурные выводы раздела должны подвести к 2.4: система разделяет принятие сервисного решения и техническое применение доступа; доменное состояние централизовано в PostgreSQL; фоновые операции используют Redis; 3x-ui API выступает внешним исполнителем провижнинга; жизненный цикл доступа можно описывать отдельно от UI и инфраструктурных деталей.

Типичные ошибки: назвать систему VPN-сервером; представить 3x-ui как внутренний модуль; скрыть факт прямого доступа backend и bot к одной БД; назвать архитектуру микросервисной без подтверждения; показать `shared` как отдельный сервис; перегрузить диаграмму классами и endpoint; включить Ansible tasks как runtime-компоненты.

Утверждения, требующие осторожности: «полная независимость backend и telegram_bot» не подтверждается из-за code-level imports; «боевой платёжный провайдер интегрирован» не подтверждается, есть demo/generic gateway; «горизонтальное масштабирование» не подтверждено compose и настройками; «атомарная синхронизация со всеми узлами» требует отдельной проверки в 2.4/3; «Ansible разворачивает весь прикладной стек» неточно — app-контейнеры подтверждены compose и GitHub Actions, а Ansible в основном готовит хосты и узлы доступа.
